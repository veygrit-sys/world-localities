# 国・地域別の更新と将来の分離

共通コードは `localities/`、住所形式は `addressing/`、原典固有のデータと処理は既存の `registries/<地域>/` に維持します。地域フォルダを `registries/` に集約し、`countries/catalog.json` で国別の入口を作ります。`training/` は学習計画の領域で、学習済みモデルを意味しません。

## 管理台帳

250の収集コードは既存の世界監査表に合わせています。主権国家数や実データ収録済み国数ではありません。`paths` は国コードのディレクトリ・ファイル名から抽出した参照候補です。複数国を含む共通ファイルの内部行までは自動抽出していません。

241コードに参照候補があり、残る9コードも台帳に保持しています。これは収録率ではありません。出典・国コードの意味・共有依存関係を国ごとに確認し、候補を更新してください。`NA` はナミビアの文字列として保持します。

| 項目 | 用途 |
|---|---|
| `storage` | 現在のリポジトリと管理方式。monorepo の ref=null はチェックアウト中の版 |
| `inventory_status` | 個別パス候補あり／共有原典の追加対応付けが必要 |
| `paths` | 国別に検査する既存ファイル。単独配布に必要な全依存ではない |
| `release_manifests` | 公開済み国別配布の管理情報。初期状態は空で、架空URLを登録しない |
| `quality` | 台帳追加による品質の引上げを防ぐ固定の未検証状態。実際の品質評価は別レポート |

## 国単位の更新

1. 国別ブランチで原典・取得日・版・利用条件・ハッシュを確認する。
2. 既存の国別処理で変換し、出典台帳・NOTICE・品質記録を更新する。
3. 変更パスを国別台帳に反映し、`python scripts/country_modules.py validate --country JP` などを実行する。
4. 該当地域の既存テストと `python -m localities layout` を実行する。共有コードを変えた場合は全関連地域も検査する。
5. 元データ件数、一意住所数、全国網羅、住所形式、配達可能性を分けてPRに記載する。

国別チェックは台帳と参照ファイルの存在を検査します。CSVの意味、親子関係、住所実在性の検査は既存の地域・出典固有テストが担当します。新しいCIは国別管理のチェックを全250コードに実行します。既存CIも保持しています。

## 大容量データの配布契約

既存の圧縮データ・分割ファイルはそのまま移行しました。今回はGit履歴の書換えやデータの外部公開を実施しません。新しい大容量原本・生成索引は通常Gitへの追加を避け、利用条件を確認して国別配布へ切り出します。

配布ごとにJSONで `schema_version: 1`、`country`、`version`、`data_schema_version`、`source_commit`（40桁）、`notice_path`、`quality_report`、`artifacts` を記録します。各artifactは `path`、HTTPSの `url`、`size`（バイト）、`sha256` を必須とします。URLは実在する公開先を確定してから登録し、期限付き認証情報を含めません。

`python scripts/country_modules.py validate-release --country JP --manifest releases/countries/JP/実際の版.json` で管理情報を検査できます。ダウンロード・ファイルの実ハッシュ照合・NOTICE同梱確認は配布時に別途実施します。今回、配布データのアップロードやモデル学習は行っていません。

## 国別リポジトリへ分離するとき

データ容量、更新頻度、担当の独立性から必要な国だけを分離します。共有コードの国別コピーやsubmoduleの大量作成は避けます。

1. 原典、コード、共有依存、NOTICE、品質レポートを一覧化する。現在の `paths` だけで全依存が揃うとは判断しない。
2. 単独の環境で取得・変換・検証・復元できることを確認する。
3. 共通データ形式と共有処理の版を固定し、国別リポジトリと配布を公開する。
4. 台帳の `storage.kind` を `external`、`repository` を公開先、`ref` を40桁コミットへ変更し、実在するrelease manifestを登録する。
5. 移行先と移行元の件数・ハッシュ・検索結果・権利表記を比較する。互換入口を残した後に、重複データの削除を別変更として扱う。

中央台帳は版と公開先の管理を担います。外部コードの自動実行や、mainの最新版への追随は行いません。分離・統合・形式変更を同時に進めず、どの版に戻せるかを記録します。
